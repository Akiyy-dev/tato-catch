# TatoTalk Windows 定点反编译结果

使用 Ghidra 12.1.4 与 Java 21，仅导入已取得的官方主程序样本。关闭自动分析和外部库加载，反汇编种子与函数体限制在先前验证的 4 个 `.pdata` 范围，每函数反编译超时上限 45 秒。没有启动、注入或读取客户端进程，没有查看任何账号、配置、数据库、消息或会话文件。

样本 SHA-256：`76c9c41b7dfac2861f3d30aea53e7a6261b136c610acddd87097dae8f1a6de58`。

项目、缓存、设置、日志和导出均保留在本地研究目录，不随源码发布。

## 完成范围

| 函数候选 RVA | 范围字节 | Ghidra 指令数 | 与 Capstone 一致 | 反编译 |
| --- | ---: | ---: | --- | --- |
| `0xdb9f80` | 1,610 | 380 | 是 | 成功 |
| `0xdb95a0` | 2,515 | 645 | 是 | 成功 |
| `0xe52c40` | 14,520 | 3,356 | 是 | 成功 |

原始 C 输出在 `ghidra-targeted-output/candidate_*.c`。自动生成名称为 `FUN_...`，仅表示地址；文件中的 `candidate_...` 名称也只是分析标签。

## 有证据支持的结构

1. 四个入口都很早从第二个 ABI 参数指向的地址 `+8` 读取 32 位值并进行多分支比较。这与按更新类型分发的结构相符，尚未从动态测试确定每个常量的真实消息类别。
2. 多个类型分支先检查第二参数地址的首个指针非零，再对指针所指对象或其 `+0x10` 位置进行处理。这给出了包装对象和负载对象分离的候选布局，不能直接当作完整消息结构。
3. `0xe52050` 的两个分支从一段起始地址、长度构造终点，以 `0x10` 为步长循环，把各元素交给 `0xe52c40`。Capstone 确认其直接调用点 RVA 为 `0xe5211b`、`0xe5251e`、`0xe5289f`、`0xe52be6`。这些结构支持其为集合更新分发路径。
4. `0xe52c40` 在 RVA `0xe54509` 与 `0xe554c0` 直接调用 `0xdb9f80`，与此前诊断字符串和静态交叉引用相互印证。

## 尚未确认

- 没有确认正文所在字段、会话 ID、消息 ID 或时间字段。
- 没有把具体比较常量认定为新私聊、新群聊或频道消息。
- 没有确认四个候选中的哪个入口可完整覆盖实时、静音和断线补收消息。
- 未进行全程序分析或被调函数反编译，因此 Ghidra 输出中的未知类型、函数签名、缺省调用参数可能不准确。应以机器指令、后续受控运行证据进一步校验。
- 当前结果不能单独证明任何地址可安全 Hook。

可继续在受控测试中仅记录入口触发次数与 `+8` 的类型值，先确认新消息是否触发。正文采集仍需要下一轮验证字段布局，并限定带唯一标记的测试消息。
